# Goal
Build ChangeOps, a local AI-assisted Git change and release controller, using HowlFrame v0.1 as a public external platform.

# Application hypothesis
Can HowlFrame v0.1 actually be used as a released platform/toolchain to build a useful application outside of the HowlFrame repository? 

# Why ChangeOps is separate from HowlFrame
To prove the platform's independence. We must consume HowlFrame through its public, released interface rather than relying on its internal implementation or development environment.

# HowlFrame version
v0.1.0

# How HowlFrame was installed/obtained
Downloaded the public `howlframe_v0.1.0_linux_amd64.tar.gz` from GitHub Releases of `howlcipher/howlframe` and installed the binary in `~/.local/bin/howlframe`.

# Starting repository state
Created a new, empty public GitHub repository `howlcipher/changeops`. Initialized a local Git repository, created a `main` branch, then switched to `agent/changeops-v01` branch. The directory structure is bare minimum (`src`, `adapter`, `config`, `tests`, `docs/journals`, `examples`).

# Architecture assumptions
- AI/user proposes a JSON configuration.
- The HowlFrame application parses the proposal, normalizes it, evaluates the policy, and determines ALLOW, DENY, or REQUIRE_APPROVAL.
- A trusted decision object is created.
- A tiny Go adapter serves as the trusted host, executing predefined bounded actions on a local git repository based on the trusted decision.

# Constraints
- Must not reach into HowlFrame internals.
- No arbitrary commands or capability bypasses via AI proposals.
- Approval binding must be to specific evaluated decisions, mitigating TOCTOU issues (stale evidence).

# Non-goals
- Full enterprise DevOps platform integration (no Jira, ServiceNow, etc. for v1).
- Cloud deployments or Terraform workflows.
- Modifying HowlFrame core unless genuinely blocked, and doing so in a separate repo/PR.
