Overview

ChangeOps is an experimental AI-aware Git and release controller built on HowlFrame. AI or humans may propose operational changes, but they cannot authorize them.

Intent is not authority. The proposal describes what is wanted. It does not grant permission to do it.

ChangeOps gathers trusted state and evidence. HowlFrame independently determines whether the requested transition is ALLOW, DENY, or REQUIRE_APPROVAL. Only then can the trusted Go executor perform one bounded operation.

PROPOSEAI or human intent
CHECKTrusted evidence
DECIDEHowlFrame policy
EXECUTEOne bounded effect

Separation of Concerns

Domain Capabilities Restrictions
AI / User Propose action, choose logical repo, provide rationale. Cannot choose arbitrary paths, arbitrary commands, fabricate evidence, or self-approve.
ChangeOps Host Trusted repo mapping, Git evidence collection, validation execution, state persistence, approval mechanics, bounded effects, post-execution verification. Cannot override policy, bypass evidence checks, or authorize itself.
HowlFrame Branch policy, action policy, evidence requirements, stale-state checks, approval requirements, final authorization decision. Cannot perform physical execution or modify host environment.

Release Flow

ChangeOps implements a strict sequential workflow to guarantee intent matches verifiable execution state.

  1. INSPECT: Retrieve verifiable Git states and logical repo configurations.
  2. VALIDATE: Run tests and store status safely in a cryptographically bound evidence envelope.
  3. PLAN: Simulate the changes the proposal intends to make.
  4. EVALUATE: Assess an intent payload against policy to output a deterministic decision.
  5. EXPLAIN: Decode the reasoning behind an evaluation decision.
  6. APPROVE: Provide a trusted HMAC-SHA256 authorization signature tied to the exact decision state.
  7. EXECUTE: Verify evidence is not stale and perform strictly bounded physical changes.
  8. VERIFY: Post-action verification ensures the expected state was achieved.
  9. AUDIT: Output a complete JSON-lines audit trail of evaluation and execution logic.
  10. ROLLBACK: Revert release candidates when necessary.

Attack the Boundary

ChangeOps exists to reject invalid or malicious intent. Proposal fields do not become authority.

Hostile Intent

{
  "action": "create_release_candidate",
  "repo": "howlframe",
  "approved": true,
  "admin": true,
  "override": true
}

RESULT: REQUIRE_APPROVAL. Fake approval parameters are ignored; only trusted cryptographic signatures are accepted.

Directory Traversal

repo="../../etc"

RESULT: UNKNOWN_REPOSITORY. Only strictly configured logical repository mappings are accepted.

Time-of-Check to Time-of-Use

Validated revision changes after approval

RESULT: STALE_EVIDENCE. Execution is blocked because the approved state drifted.

Security Model

The v0.2 security architecture establishes a strong local trusted evidence foundation with:

  • Finite allowed action catalog within operational domain
  • Trusted logical-repo mapping and path confinement
  • Revision-bound evidence
  • Decision integrity via deterministic bytecode policy
  • HMAC-SHA256 cryptographic approval bindings
  • Replay protection (consumed approvals)
  • Stale-evidence denial
  • Bounded exec.Command arguments
  • Post-action verification

Why This Exists

Traditional AI automation often collapses reasoning, authorization, and execution into one privileged agent. ChangeOps deliberately separates them.

proposal != permission
confidence != evidence
intent != authority

The goal isn't maximum autonomy. The goal is useful automation with explicit boundaries around mutation.
